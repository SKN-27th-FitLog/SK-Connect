# 코드 무결성 및 테스트 기준

본 문서는 **post_analysis**를 포함한 프로젝트 구현 코드의 무결성, 안정성, 유지보수성, 테스트 가능성을 확보하기 위한 **범용 기준**을 정의한다.

작업 전·후에 본 문서와 [design.md](design.md)를 함께 보고, 함수 계약·테스트 케이스·실행 안전성 등급이 충족되는지 확인한다.

---

## 목적


| 목표        | 설명                           |
| --------- | ---------------------------- |
| 동작 기준 명확화 | 구현 코드가 무엇을 보장하는지 문서화         |
| 테스트 기준 통일 | 케이스 작성·검증 방식을 프로젝트 전반에 일관 적용 |
| 회귀 방지     | 수정 후 기존 기능·핵심 규칙 유지          |
| 안전한 테스트   | 실제 운영 데이터 손상 없이 검증           |
| 검증 규칙 일관성 | 레이어·함수 유형별로 동일한 절차 적용        |


---

## 1. 테스트의 목적

테스트는 단순히 “에러가 발생하지 않는지”를 확인하는 작업이 **아니다**.


| #   | 핵심 질문                        |
| --- | ---------------------------- |
| 1   | 입력에 대해 **기대한 결과**가 생성되는가     |
| 2   | 잘못된 입력을 **안전하게** 처리하는가       |
| 3   | **경계값**에서도 안정적으로 동작하는가       |
| 4   | 코드 수정 이후 **기존 기능**이 유지되는가    |
| 5   | **외부 환경** 변화에도 일관성을 유지하는가    |
| 6   | 프로젝트의 **핵심 규칙(불변)**이 깨지지 않는가 |


---

## 2. 테스트 이전에 필요한 작업

테스트 코드를 작성하기 **전에** 반드시 함수별 **계약(Function Contract)**을 정의해야 한다.

> 테스트는 함수 계약을 검증하는 수단이며, **계약이 없는 테스트는 기준이 불명확**해진다.

**필수 순서** (순서 변경 금지):

```
함수 계약 정의
  → 검증 기준 정의
  → 테스트 케이스 정의
  → 테스트 코드 구현
```

---

## 3. 함수 계약(Function Contract)

모든 공개·핵심 함수는 아래 항목을 정의한다.

### 3.1 기본 계약 항목


| 항목         | 설명                               |
| ---------- | -------------------------------- |
| 함수명        | 식별자                              |
| 함수 유형      | [§4 함수 유형 분류](#4-함수-유형-분류-기준) 참조 |
| 책임         | 이 함수가 담당하는 단일 책임                 |
| 입력         | 타입·제약·nullable 여부                |
| 출력         | 반환 타입·의미                         |
| 정상 조건      | 성공으로 간주하는 입력·상태                  |
| 실패 조건      | 실패로 간주하는 입력·상태                   |
| 불변 규칙      | 항상 지켜야 하는 비즈니스·포맷 규칙             |
| 부작용        | DB·파일·API·로그 등 외부 영향             |
| 에러 처리 방식   | 예외 타입·로그·fallback                |
| 테스트 필요 케이스 | 최소로 검증할 시나리오 목록                  |


### 3.2 계약 정의 예시

```text
함수명: save_url
함수 유형: 데이터 변환 + 저장

책임:
  URL 문자열을 HTML a 태그 형태로 변환 후 저장한다.

입력:
  url: str

출력:
  저장된 URL 객체 또는 저장 성공 여부

정상 조건:
  - 유효한 URL 문자열
  - 중복되지 않은 URL

실패 조건:
  - None
  - 빈 문자열
  - URL 형식 불일치

불변 규칙:
  모든 URL은 반드시 아래 형태로 저장되어야 한다.
  <a href="URL">URL</a>

부작용:
  DB insert 발생

에러 처리 방식:
  유효하지 않은 URL은 ValueError 발생

테스트 필요 케이스:
  - 정상 URL
  - 빈 문자열
  - None
  - 중복 URL
  - 이미 a 태그가 포함된 URL
```

계약은 `docs/contracts/` 등 별도 파일로 분리해도 되며, 함수 docstring에 요약을 두고 상세는 문서로 링크하는 방식을 권장한다.

## 4. 함수 유형 분류 기준

모든 함수는 아래 유형 **중 하나 이상**으로 분류한다. 유형에 따라 **검증 기준**이 달라진다.

### A. 순수 계산 함수

외부 상태를 변경하지 않고 입력값만으로 결과를 생성한다.

**예:** 문자열 정규화, 날짜·점수 계산


| 검증 기준         |
| ------------- |
| 동일 입력 → 동일 출력 |
| 부작용 없음        |
| 입력 타입 검증      |
| 경계값 처리        |


### B. 데이터 변환 함수

데이터 구조 또는 포맷을 변환한다.

**예:** DTO 변환, JSON 변환, URL 태그 생성


| 검증 기준        |
| ------------ |
| 필수 필드 존재     |
| 변환 후 스키마 일치  |
| 타입 변환 가능 여부  |
| 원본 데이터 훼손 없음 |


### C. 검증 함수

입력 데이터의 유효성을 검증한다.

**예:** `validate_url`, `validate_post_schema`


| 검증 기준      |
| ---------- |
| 정상 데이터 통과  |
| 비정상 데이터 실패 |
| 실패 사유 명확성  |


### D. 저장/조회 함수

DB 또는 저장소와 상호작용한다.

**예:** `save_post`, `find_post`, `merge_analysis_data`


| 검증 기준          |
| -------------- |
| 저장·조회 성공 여부    |
| 중복 처리          |
| rollback 가능 여부 |
| 조회 결과 정확성      |


### E. 외부 연동 함수

외부 API·외부 시스템과 연결된다.

**예:** 크롤링, OpenAI 호출, Webhook


| 검증 기준       |
| ----------- |
| 타임아웃 처리     |
| 응답 포맷 변경 대응 |
| 실패 재시도 여부   |
| 예외 처리       |


### F. 오케스트레이션 / 핸들러 함수

여러 단계를 조합하여 실행 흐름을 제어한다.

**예:** `run_pipeline`, Lambda Handler, Dispatch


| 검증 기준       |
| ----------- |
| 실행 순서 보장    |
| 중간 실패 처리 기준 |
| 단계별 결과 전달   |
| 로그 추적 가능 여부 |

## 5. 실행 안전성 기준

테스트 설계 시 **실제 데이터 영향 여부**를 반드시 정의한다. 모든 함수에는 **실행 안전성 등급**을 부여한다.

---

## 6. 실행 안전성 등급


| 등급          | 명칭       | 특징                        | 테스트 방식                    |
| ----------- | -------- | ------------------------- | ------------------------- |
| **Level 0** | 순수 함수    | 실제 데이터 영향 없음, 외부 상태 접근 없음 | 입력·출력 비교                  |
| **Level 1** | 읽기 전용    | 읽기만, 수정 없음                | fixture, 테스트 전용 데이터       |
| **Level 2** | 임시 상태 변경 | rollback 가능한 변경           | 테스트 DB, 트랜잭션 rollback     |
| **Level 3** | 외부 부작용   | 복구 어렵거나 제한적               | mock/stub/fake, dry-run   |
| **Level 4** | 파괴적      | 데이터 손실·복구 곤란              | sandbox만, 운영 직접 실행 **금지** |


### 등급별 예시


| 등급  | 예시                                              |
| --- | ----------------------------------------------- |
| 0   | 문자열 처리, 정규화, BERT 토큰화(메모리만), shop 매칭 필터 로직      |
| 1   | `get_crawling_data`, `get_analysis_data`, 파일 읽기 |
| 2   | `merge_analysis_data`, 테스트 DB insert/update     |
| 3   | LangChain/OpenAI 호출, 실제 HTTP 크롤링                |
| 4   | 운영 DB 대량 delete, 인덱스 초기화, 운영 파일 삭제              |


**원칙:** 등급이 높을수록 단위 테스트에서는 **격리**(mock·전용 DB·dry-run)하고, 통합 테스트는 **비운영** 환경에서만 수행한다.

## 7. 테스트 가능 구조 설계 원칙

테스트 가능성을 위해 구현을 다음 **레이어 순서**로 분리하는 것을 권장한다.

```
판단 로직 → 데이터 변환 로직 → 실제 실행 로직 → 외부 반영 로직
```


| 단계         | 예시               | 권장 등급   |
| ---------- | ---------------- | ------- |
| URL 문자열 검증 | 형식·빈 값 검사        | Level 0 |
| URL 태그 생성  | HTML 변환          | Level 0 |
| 저장 객체 생성   | DataFrame/레코드 구성 | Level 0 |
| DB 저장      | MERGE/INSERT     | Level 2 |
| 외부 API 전송  | LLM·Webhook      | Level 3 |
| 운영 데이터 삭제  | 대량 DELETE        | Level 4 |


**post_analysis 레이어 정렬** ([design.md](design.md)와 동일):

- `common/`: Level 0 중심(상수, BERT, 에러 메시지) — `postgresql` 미의존
- `postgresql/`: Level 1~2(조회·MERGE)
- 루트 스크립트·`pipeline.py`: Level 2~3 조합(F)

판단·변환은 `common` 또는 스크립트 내 **순수 함수**로 두고, DB·LLM은 얇은 어댑터 뒤에 두면 mock이 쉬워진다.

## 8. 테스트 케이스 최소 구성 기준

모든 테스트 케이스 문서(또는 docstring)는 아래 항목을 포함한다.


| 필드     | 설명                      |
| ------ | ----------------------- |
| 테스트 ID | 고유 식별자 (예: `PA-GR-001`) |
| 테스트 대상 | 함수·모듈명                  |
| 목적     | 무엇을 검증하는지 한 줄           |
| 사전 조건  | DB 상태, env, fixture     |
| 입력     | 구체적 값·파일                |
| 실행 절차  | 호출 순서                   |
| 기대 결과  | 출력·DB·로그                |
| 검증 기준  | pass/fail 판단 규칙         |
| 실패 조건  | 이 경우 테스트 실패             |
| 비고     | mock 여부, 등급, 이슈 링크      |

## 9. 최소 테스트 분류 기준

모든 구현은 최소한 아래 **네 가지**를 고려한다.


| 분류          | 설명              | 예시                           |
| ----------- | --------------- | ---------------------------- |
| **정상 케이스**  | 정상 입력 → 기대 결과   | 유효 URL 저장                    |
| **실패 케이스**  | 비정상 입력 → 예상된 실패 | `None`, 빈 문자열 → `ValueError` |
| **경계값 케이스** | 0개 / 1개 / 최대·최소 | `max_rows=1`, 처리 대상 0건       |
| **불변성 케이스** | 반드시 유지되는 규칙     | MERGE 키, 컬럼명 Enum, 감성 코드     |
| **회귀 케이스**  | 과거 버그 재발 방지     | 버그 수정 시 **반드시** 케이스 추가       |

## 10. 테스트 코드 작성 원칙

1. **독립 실행** — 다른 테스트 결과에 의존하지 않는다.
2. **순서 비의존** — 실행 순서를 가정하지 않는다.
3. **운영 데이터 비접촉** — 실제 운영 DB·API 키·프로덕션 경로를 사용하지 않는다.
4. **기대 결과 명확** — assert 메시지로 실패 원인을 알 수 있다.
5. **추적 가능** — 실패 시 입력·중간 상태를 로그 또는 fixture로 재현 가능하다.
6. **구현 비결합** — 내부 private 세부 구현이 아닌 **계약(입출력·불변)**을 검증한다.
7. **규칙 설명 가능** — 테스트 이름만으로 “어떤 프로젝트 규칙”을 지키는지 설명할 수 있다.

**권장 도구:** `pytest`, fixture, `monkeypatch`/`unittest.mock`(Level 3), 트랜잭션 rollback 또는 테스트 DB(Level 2).

## 12. 최종 목표

다음 상태에 도달하는 것이 본 기준의 **완료 조건**이다.

- 함수의 **책임**이 명확하다
- **실패 조건**이 명확하다
- **테스트 기준**이 팀·모듈 간 일관적이다
- **실제 데이터 손상 없이** 테스트 가능하다
- 코드 수정 시 **회귀**를 방지할 수 있다
- 프로젝트 **핵심 규칙**이 문서·테스트에 반영되어 있다

### 불변 규칙 (design.md와 연동)

- `common/constant.py` 컬럼명·코드 Enum과 DataFrame 컬럼 일치
- `PostAnalysisErrors`에 정의된 실패·경고 메시지와 동작 일치
- analysis MERGE 시 키·갱신 컬럼은 `postgresql/config.py` SQL과 일치

- LLM 단계: `max_rows` 상한·IC02 제외 등 파이프라인 필터 규칙

### 테스트 디렉터리

현재 `tests/` 및 자동화 테스트는 **미구현** 상태이다. §11 순서에 따라 계약 정의 후 `tests/` 추가를 권장한다.
