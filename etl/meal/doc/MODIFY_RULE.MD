---

# ⚠️ 주의사항 (Important Considerations)

## 1. 로더(Loader) 다이어트는 “기능 제거”가 아니다

로더 다이어트는 로더의 책임을 단순화하기 위한 것이지,
프로젝트의 핵심 기능까지 제거하는 것을 의미하지 않는다.

특히 다음과 같은 오해를 방지해야 한다:

* ❌ 로더는 DB 적재만 해야 한다 → 무조건적인 축소 해석
* ⭕ 로더는 불필요한 책임을 제거하되, 필수 기능은 유지해야 한다

---

## 2. 하이브(Hive) 방식 CSV 저장 로직은 필수 유지 대상이다

본 프로젝트에서 로더 내부의 **Hive-style 원본/정제 데이터 CSV 저장 로직은 선택 사항이 아니라 필수 요구사항이다.**

따라서 리팩토링 시에도 해당 로직은:

* 제거 ❌
* 단순화로 인해 손실 ❌
* 임시 저장 방식으로 대체 ❌

되어서는 안 되며, 반드시 유지되어야 한다.

---

## 3. 하이브 폴더 구조 규칙 (필수 준수)

현재 프로젝트는 다음과 같은 Hive-style 디렉토리 구조를 사용한다:

```text
process=cleansing/service=shop/year=2026/month=04/day=14/status=success/203045.csv
```

### 구조 설명

| 파라미터           | 의미                                   |
| -------------- | ------------------------------------ |
| process        | 데이터 처리 단계 (raw / cleansing / load 등) |
| service        | 데이터 도메인 또는 서비스 단위 (예: shop)          |
| year/month/day | 데이터 생성 또는 처리 기준 날짜                   |
| status         | 처리 결과 상태 (success / fail 등)          |
| 파일명            | 실행 시각 또는 배치 식별자 기반                   |

이 구조는 단순한 저장 방식이 아니라 다음 목적을 가진다:

* 데이터 추적 (Traceability)
* 배치 단위 관리
* 장애 발생 시 원인 분석
* 재처리 가능성 확보
* 파티셔닝 기반 조회 최적화

따라서 해당 구조는 반드시 유지되어야 한다.

---

## 4. 로더의 책임 재정의 (중요)

본 프로젝트에서 로더의 역할은 단순한 DB insert 수행이 아니다.

### 로더의 필수 책임

1. Hive 방식 디렉토리에 CSV 파일 저장
2. DB에 데이터 적재
3. 적재 결과 반환 또는 기록

즉 로더는 다음과 같이 정의된다:

> “데이터를 공식 저장 포맷(Hive 구조)으로 보존하고, 이후 DB에 적재하는 단계”

---

## 5. 오케스트레이터(Orchestrator)와의 책임 충돌 방지

오케스트레이터를 투명하게 구성하더라도,
로더 내부의 Hive 저장 로직을 외부로 분리하면 안 된다.

### 잘못된 구조 (금지)

* 오케스트레이터가 직접 raw 파일 저장
* 로더는 단순 DB insert만 수행
* 저장 정책이 여러 위치로 분산됨

### 올바른 구조

* 오케스트레이터: 흐름 제어 (단계 호출)
* 로더: 저장 정책 + DB 적재 책임 유지

---

## 6. 파일 저장 성공 ≠ DB 적재 성공

CSV 파일이 정상적으로 저장되었다고 해서
DB 적재가 성공한 것은 아니다.

반드시 아래 검증이 필요하다:

* INSERT 수행 여부 확인
* commit 여부 확인
* 적재 건수 검증
* 실제 데이터 조회

### 검증 예시

```sql
-- 전체 건수 확인
SELECT COUNT(*) FROM target_table;

-- 특정 배치 기준 확인
SELECT COUNT(*)
FROM target_table
WHERE batch_id = '20260414';

-- 최신 데이터 확인
SELECT *
FROM target_table
ORDER BY created_at DESC
LIMIT 5;
```

---

## 7. Raw / Cleansing / Load 데이터 경계 명확화

Hive 구조를 사용할 경우, 각 단계의 데이터 의미를 명확히 구분해야 한다.

| 단계        | 설명              |
| --------- | --------------- |
| raw       | 수집 직후 원본 데이터    |
| cleansing | 전처리 완료 데이터      |
| load      | DB 적재 기준 최종 데이터 |

이 구분이 없으면:

* 데이터 재현 불가능
* 디버깅 어려움
* 운영 혼란 발생

---

## 8. 재실행(Replay) 정책 반드시 정의

동일한 조건으로 배치를 재실행할 경우를 반드시 고려해야 한다.

확인해야 할 사항:

* 동일 경로에 파일 저장 시 덮어쓰기 여부
* timestamp 기반 파일 생성 여부
* DB 적재 시 중복 처리 방식 (append / upsert)
* 실패 배치 재처리 전략

이 정책이 없으면:

* 데이터 중복
* 데이터 유실
* 운영 불안정

문제가 발생할 수 있다.

---

## 9. 저장 규칙은 반드시 문서로 유지해야 한다

Hive 저장 로직이 코드에만 존재하면
리팩토링 과정에서 쉽게 훼손될 수 있다.

따라서 반드시 다음을 문서화해야 한다:

* 저장 경로 규칙
* 폴더 네이밍 정책
* 파일명 규칙
* 상태(status) 기준 정의
* 인코딩 및 CSV 포맷 규칙

---

## ✔️ 핵심 요약

* 로더 다이어트는 기능 제거가 아니다
* Hive 방식 CSV 저장 로직은 필수 유지 대상이다
* 오케스트레이터는 흐름만 담당하고 저장 정책은 침범하지 않는다
* 파일 저장과 DB 적재는 반드시 분리해서 검증해야 한다
* 저장 구조, 재실행 정책, 데이터 단계 구분은 반드시 문서화해야 한다

# 📊 모듈화 반영 및 분석 (Modularization Analysis)

기존에 제안했던 리팩토링 계획을 `MODIFY_RULE.MD`의 지침에 따라 재검토한 결과입니다.

## 1. 반영해야 할 핵심 변경 사항 (Must Include)

*   **로더의 책임 유지 (Rule 4, 5)**: 
    *   기존 계획에서는 오케스트레이터의 투명성을 위해 CSV 저장 로직을 외부로 꺼내려 했으나, 이는 **절대 금지** 사항임을 확인했습니다.
    *   따라서 모든 `Loader` 클래스(`ShopLoader`, `ReviewLoader` 등)는 내부에서 `file_manager`를 호출하여 **Hive 구조에 맞게 CSV를 저장하는 로직을 반드시 유지**합니다.
*   **DB 적재 검증 강화 (Rule 6)**: 
    *   `verification-before-completion` 시 단순히 에러 유무만 체크하는 것이 아니라, `psycopg2`를 통해 실제 DB의 상위 5건 데이터 및 총 건수를 조회하여 정합성을 증명하겠습니다.
*   **파일 저장과 DB 적재의 논리적 분리**: 
    *   로더 내부 로직이 `CSV 저장 성공 -> DB 적재 시도` 순서로 명확히 작동하게 하여, 한 단계가 실패하더라도 원인 파악이 가능하도록 구현합니다.

## 2. 기존 계획에서 수정/취소해야 할 부분 (To Modify/Cancel)

*   **[취소] 오케스트레이터의 파일 저장 직접 제어**: 
    *   오케스트레이터는 "수집(Extract)", "정제(Transform)", "적재(Load)"의 **순서만 제어**하며, 파일 저장이라는 "정책"은 로더 모듈 내부에 캡슐화된 상태를 유지합니다.
*   **[수정] 로더의 슬림화 방향**: 
    *   로더에서 "불필요한 책임"을 제거하는 것은 `sys.path` 관리나 복잡한 초기화 로직 등에 국한되며, **데이터 레이크 저장 및 DB 적재라는 두 가지 핵심 책임은 통합된 상태**로 유지합니다.

## 3. 굳이 안 해도 될 부분 (Not Needed)

*   **Config 폴더의 과도한 세분화**: 
    *   현재의 `.env` 방식이 프로젝트의 `Modify Rule`을 침해하지 않는다면, 무리하게 별도의 복잡한 YAML 설정 레이어를 추가할 필요는 없습니다. (기존의 직관적인 방식 유지)
