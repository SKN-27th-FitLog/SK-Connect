1. 핵심 설계 원칙

1) Exception / Reason / Action 분리

- Exception:
  실패의 "의미"만 정의한다.
  (reason_code, stage, entity_type, detail 포함)

- Resolver:
  action, severity, retry 정책을 결정한다.

- Stage:
  정책 판단을 하지 않는다.
  Exception을 발생시키고 전달만 한다.

- Fail 처리 흐름:
  Exception 발생
  → Resolver에서 action 결정
  → Fail Ledger 기록
  → CloudWatch 로그 출력


--------------------------------------------------
2. Exception 정의 원칙
--------------------------------------------------

- Exception은 action을 직접 가지지 않는다.
- Exception은 Resolver가 판단할 수 있도록 충분한 context를 제공해야 한다.

필수 포함 정보:
- reason_code
- stage
- entity_type
- detail


--------------------------------------------------
3. reason_code vs exception 역할 정의
--------------------------------------------------

Exception:
- 시스템 에러 (흐름 중단)
- 예: NETWORK_ERROR, DB_CONNECTION_ERROR

reason_code:
- 데이터 품질 / 판정 결과 (흐름 유지)
- 예:
  AMBIGUOUS_MENU_NAME
  UNDEFINED_CODE_DETECTED
  MISSING_NORMALIZED_ADDRESS


--------------------------------------------------
4. 정책 적용 구조 (Source of Truth)
--------------------------------------------------

- 정책표 문서: 설계 기준서
- Resolver 코드: 실제 실행 기준 (Source of Truth)

→ 모든 action 결정은 resolver에서 수행


--------------------------------------------------
5. Action 정의
--------------------------------------------------

retry:
- 환경 문제
- 다음날 동일 로직 재시도

reprocess:
- 데이터 문제
- 룰 수정 또는 운영 개입 후 재처리

drop:
- 영구 실패
- 재처리 대상 제외

load_with_warning:
- 적재는 진행
- 품질 이슈 기록

alert_only:
- 운영 알림만 수행


--------------------------------------------------
6. reprocess 세부 분류
--------------------------------------------------

1) 자동 reprocess
- selector 수정
- normalization rule 수정
- 코드 테이블 보강

→ 코드 수정 없이 룰 변경으로 해결

2) 수동 reprocess
- raw 데이터 자체 문제
- source 변경
- 사람 검토 필요


--------------------------------------------------
7. Load 결과 확장 필드
--------------------------------------------------

partial_failure_flag:
- 일부 실패 여부

entity_completeness:
- 데이터 완성도 (0~1)

예:
menu_expected = 10
menu_loaded = 6
entity_completeness = 0.6


--------------------------------------------------
8. Idempotency 규칙
--------------------------------------------------

1) Fail Ledger 중복 방지 키

(batch_id, stage, entity_type, entity_id, reason_code)

→ 동일 이벤트 1회만 기록


2) Store Load

- 동일 dedup_key 발생 시
→ insert가 아닌 upsert (update)


3) Raw 저장

- overwrite 금지
- 항상 신규 파일 생성


4) Retry Item 중복 방지 키

(batch_id, entity_id, action)


--------------------------------------------------
9. Transaction 경계
--------------------------------------------------

store:
- 1 트랜잭션
- 실패 시 전체 rollback

menu:
- 별도 트랜잭션
- 일부 실패 허용

review:
- 별도 트랜잭션
- 일부 실패 허용

fail ledger:
- 비즈니스 트랜잭션과 분리


--------------------------------------------------
10. Dedup 정책 보완
--------------------------------------------------

- dedup_rule_version 필수 추가

이유:
- 정규화 룰 변경 시 동일 store 판정 변화 가능


--------------------------------------------------
11. 모니터링 및 알람 정책
--------------------------------------------------

기준:

1) fail_count ≥ 100
→ Slack warning

2) load_success_rate < 80%
→ Slack critical

3) fail_rate 기준 추가
→ 20% 이상 시 알람

알람 포함 정보:
- batch_id
- category_cd
- fail_count
- load_success_rate
- 주요 reason_code


--------------------------------------------------
12. 파일 저장 및 Lifecycle 정책
--------------------------------------------------

파일 포맷:

- Raw: html/json/text
- Candidate/Normalized/Fail Ledger: JSONL
- Metrics: 집계 파일

보관 정책:

- raw: 30일
- candidate: 14일
- normalized: 30일
- fail ledger: 90일
- metrics: 영구


--------------------------------------------------
13. 보안 정책
--------------------------------------------------

DB 정보:
- Secret Manager 사용

로컬:
- .env 허용

Raw 데이터:
- 저장 허용 (증거 데이터)

Fail Ledger:
- source_url 저장 허용

금지:
- cookie
- auth header
- 민감 인증 정보 저장

로그:
- 민감정보 마스킹


--------------------------------------------------
14. 핵심 설계 철학
--------------------------------------------------

- 정책은 코드에 하드코딩하지 않는다.
- 정책은 resolver 또는 config에서 관리한다.
- 코드는 실행 로직만 담당한다.

핵심 원칙:

“세세하게 정하되, 코드 밖으로 분리한다.”
