크롤링 재설계 명세서 (개정 초안 v4)

본 문서는 기존 초안 v1을 기반으로 운영 환경 제약과 배포 전략을 반영하여 수정한 개정 초안이다.
기존 초안의 단계 분리 원칙은 유지하되, 실제 운영 기준은 AWS 배포, 일일 수집 정책, 재수집 규칙,
Hive 경로 정책, 상태별 독립 실행 구조, DB 코드 테이블 조회 원칙을 중심으로 재정의한다.

==================================================
1. 개요
==================================================

본 시스템은 음식점 데이터를 수집·가공·검증·적재하는 다단계 크롤링 파이프라인이다.

이 시스템은 다음 운영 조건을 반드시 만족해야 한다.

1) AWS 환경에 배포 가능해야 한다.
2) 크롤링 로직은 AWS Layer에 포함하여 재사용 가능하게 구성해야 한다.
3) 스케줄러 또는 핸들러를 통해 각 상태(Stage/Status)를 독립적으로 실행할 수 있어야 한다.
4) 코드 테이블(category_cd 등)은 상수화하지 않고 DB에서 직접 조회해야 한다.
5) 쿼리문 자체는 상수화한다.
6) global 변수는 사용하지 않는다.
7) 로깅은 logger 모듈을 사용하며, 별도 래퍼 함수를 만들지 않는다.
8) 모든 처리 결과는 성공/실패/재처리 가능 여부를 구조적으로 추적할 수 있어야 한다.

==================================================
2. 운영 배포 아키텍처 원칙
==================================================

2.1 AWS 배포 방향

시스템은 AWS 상에서 자동 수집이 가능하도록 설계한다.

권장 배포 구조
- 실행 단위: AWS Lambda 또는 Lambda 기반 핸들러
- 공통 의존성 및 크롤링 라이브러리: AWS Layer
- 스케줄링: EventBridge Scheduler 또는 후속 오케스트레이션 핸들러
- 저장 경로: S3 또는 이에 준하는 객체 저장소
- DB 적재: RDS 또는 운영 DB 연결

핵심 원칙
- 크롤링 공통 모듈은 Layer에 올릴 수 있도록 독립 패키지 형태를 유지한다.
- 실행 코드는 핸들러 중심으로 분리하여 상태별 개별 실행이 가능해야 한다.
- 특정 상태만 재실행할 수 있어야 한다.
- 배치 전체 실패 시에도 일부 상태 또는 일부 카테고리만 재수행 가능해야 한다.

2.2 AWS Layer 설계 목적

AWS Layer에는 다음과 같은 공통 요소를 포함한다.

예시
- HTML 수집기
- 렌더링 수집기
- 파서 공통 유틸
- validator 공통 유틸
- DB 연결 공통 모듈
- S3/Hive 경로 생성 유틸
- 공통 모델 정의
- 로깅 설정 모듈
- Exception class 정의
- failure resolver
- fail ledger builder
- structured logging formatter
- action 판정은 resolver가 담당한다.
- CloudWatch가 알람을 담당한다.

주의
- Layer에는 공통 재사용 로직만 둔다.
- 환경별 설정값은 Layer 내부에 하드코딩하지 않는다.
- 카테고리 코드, 서비스 코드, 테이블 값 등 운영 데이터는 DB 조회 또는 설정 주입으로 처리한다.

3. 일일 수집 운영 정책
==================================================

3.1 수집 기준

일일 수집은 코드 테이블의 category_cd를 기준으로 수행한다.

정책
- category_cd별로 매일 100개씩 수집한다.
- 하루 수집 대상 100개는 매일 다른 내용이어야 한다.
- 과거에 이미 성공적으로 DB 적재된 가게는 당일 신규 수집 대상에서 제외한다.
- 수집 단위는 "가게(store)" 기준이다.
- 메뉴/리뷰는 해당 가게의 종속 엔티티로 본다.

3.2 중복 제외 기준

중복 제외 기준은 단순 수집 성공이 아니라 DB 적재 성공 여부를 기준으로 판단한다.

제외 대상
- 이전 실행에서 최종 DB 적재까지 성공한 store

제외하지 않는 대상
- 수집 실패한 store
- 파싱 실패한 store
- 검증 실패한 store
- 적재 실패한 store
- fail reason에 따라 재시도 가능 대상인 store

즉, "이미 본 적 있는 가게"가 아니라 "최종 적재가 성공한 가게"만 제외 대상이다.

3.3 부족분 보충 규칙

어떤 category_cd에서 목표 100건 중 일부가 실패하면,
실패 사유와 정책에 따라 해당 가게 포함 여부를 판단하여 100건을 채워야 한다.

원칙
- 목표는 category_cd당 최종 처리 대상 100건 확보이다.
- 이미 성공 적재된 가게를 제외하고 후보를 계속 추가 탐색한다.
- 실패 데이터는 fail reason에 따라 재포함 여부를 결정한다.
- 재포함 가능 대상은 다시 모집단에 넣어 100건 충족을 시도한다.

예시
- 목표: category_cd = CA01, 하루 100건
- 실제 1차 시도: 100건 수집
- 결과: 82건 성공, 18건 실패
- 실패 18건 중 retry/reprocess 대상이 있으면 정책에 따라 다시 포함
- 그래도 부족하면 신규 후보를 추가 수집
- 최종적으로 성공 적재 100건 또는 더 이상 수집 가능한 후보 없음 상태까지 진행

==================================================
4. 실패 데이터 재수집 정책
==================================================

4.1 기본 원칙

실패 데이터는 무조건 폐기하지 않는다.
실패 사유(reason_code/action)에 따라 다음 행동을 분리한다.

action 종류
- drop
- retry
- reprocess

4.2 실패 가게의 재포함 원칙

실패한 가게는 fail 이유에 따라 당일 100건 확보를 위한 재수집 후보에 포함될 수 있다.

재포함 가능 예
- NETWORK_ERROR
- TIMEOUT
- TEMPORARY_RENDER_FAIL
- DB_CONNECTION_ERROR
- TRANSIENT_INSERT_ERROR
- SELECTOR_MISMATCH (구조 복구 가능 시)

재포함 제외 예
- INVALID_URL
- NOT_RESTAURANT_ENTITY
- DUPLICATED_SUCCESS_STORE
- PERMANENT_SCHEMA_VIOLATION
- BLOCKED_SOURCE_POLICY

중요 원칙
- 재포함 여부는 status가 아니라 reason_code/action 기준으로 결정한다.
- 동일 가게를 무한 재시도하지 않도록 재시도 횟수 제한이 필요하다.
- 재시도 횟수, 마지막 실패 시간, 마지막 reason_code는 별도 추적해야 한다.

==================================================
5. 상태별 독립 실행 구조
==================================================

5.1 설계 목표

향후 핸들러를 설정할 예정이므로,
각 상태(Stage 또는 실행 상태)는 독립 실행 가능해야 한다.

즉, 다음이 가능해야 한다.

- raw 수집만 실행
- candidate parsing만 실행
- validation/normalization만 실행
- load만 실행
- fail 데이터에 대해서만 retry 실행
- 특정 category_cd만 실행
- 특정 날짜 partition만 재실행
- 특정 status만 재처리

5.2 독립 실행을 위한 원칙

각 상태는 다음 조건을 만족해야 한다.

1) 입력과 출력이 명확해야 한다.
2) 이전 상태의 산출물 경로를 명시적으로 받는다.
3) 함수 내부에서 외부 global 상태를 참조하지 않는다.
4) 상태 간 전달은 파일/S3 path + 명시적 payload 기반으로 한다.
5) 특정 상태만 재실행해도 부작용이 최소화되어야 한다.

5.3 권장 실행 단위

예시 실행 단위
- collect_raw_handler
- parse_candidate_handler
- validate_normalize_handler
- load_handler
- retry_fail_handler
- daily_category_collection_handler

6. Hive 경로 정책
==================================================

6.1 경로 원칙

모든 성공/실패 파일은 Hive 스타일 경로를 사용한다.

예시
crawling=raw / service=shop / year=2026 / month=04 / day=14 / status=fail / HHMMSSmmm.csv

운영에서는 실제 경로 구분자를 표준 파일시스템 또는 객체 저장소 기준으로 사용한다.

예시
crawling=raw/service=shop/year=2026/month=04/day=14/status=fail/201530123.csv

6.2 경로 구성 요소

필수 partition
- crawling
- service
- year
- month
- day
- status

권장 추가 요소
- category_cd
- stage
- batch_id

예시
crawling=normalized/service=shop/year=2026/month=04/day=14/status=success/category_cd=CA01/stage=validation/201530123.csv

6.3 status 값 원칙

status는 독립 partition으로 관리한다.

예시 status
- success
- fail
- retry
- reprocess
- dropped

주의
- status는 단순 로깅용 값이 아니라 후속 핸들러가 직접 읽을 수 있는 파티션 키여야 한다.
- 따라서 status 정의는 운영 관점에서 안정적으로 유지해야 한다.

==================================================
7. 파이프라인 구조 (개정)
==================================================

기본 흐름
Stage 0: Daily Target Selection
→ Stage 1: Raw Collection
→ Stage 2: Candidate Parsing
→ Stage 3: Validation & Normalization
→ Stage 4: Load
→ Stage 5: Fail Classification / Retry Scheduling

7.1 Stage 0. Daily Target Selection

목적
- category_cd별 일일 수집 대상 100건 선정
- 이미 성공 적재된 store 제외
- fail 정책에 따라 재포함 후보 반영
- 당일 수집 모집단 확정

입력
- 코드 테이블(category_cd)
- 기존 성공 적재 store 목록
- fail store 목록 및 마지막 reason/action
- 수집 후보 소스

출력
- category_cd별 당일 수집 대상 목록
- batch_id
- target metadata

실패 결과
- status = fail
- stage = target_selection
- reason_code 기록

7.2 Stage 1. Raw Collection

기존 원칙 유지 + AWS 환경 고려

추가 원칙
- 원시 응답은 반드시 재현 가능한 형태로 저장
- 수집기 타입(http/render/public_source)을 기록
- Lambda 재시도와 비즈니스 retry를 구분해야 한다

7.3 Stage 2. Candidate Parsing

기존 원칙 유지

추가 원칙
- raw의 증거성을 손상시키지 않는다
- 추출 실패 시 selector/DOM 구조 관련 detail을 남긴다

7.4 Stage 3. Validation & Normalization

기존 원칙 유지

추가 원칙
- 코드값 정규화가 필요할 경우 상수 매핑이 아니라 코드 테이블 조회 결과를 사용한다
- 단, 매 실행마다 불필요한 과도한 조회가 발생하지 않도록 세션 범위 캐시 또는 실행 단위 캐시까지는 허용할 수 있다
- 이 캐시는 global 상수가 아니어야 하며 실행 컨텍스트 내부 객체로 관리한다

7.5 Stage 4. Load

기존 원칙 유지

추가 원칙
- DB 적재 전 코드 테이블을 직접 조회해서 참조 무결성을 확인한다
- code table 값은 코드 상수로 박아넣지 않는다
- INSERT/UPSERT 쿼리문은 상수화한다
- 테이블 구조가 고정이므로 SQL 문자열 상수 관리 방식은 허용한다

7.6 Stage 5. Fail Classification / Retry Scheduling

목적
- 실패를 운영 가능한 작업 단위로 분류
- retry/reprocess/drop 후속 대상 확정
- 다음 실행 핸들러가 읽을 수 있는 상태 파일 생성

출력
- fail ledger
- retry 대상 목록
- reprocess 대상 목록
- drop 대상 목록

8. 코드 테이블 조회 원칙
==================================================

8.1 절대 원칙

코드 테이블(category_cd 포함)은 상수화하지 않는다.

금지
- CATEGORY_MAP = {...}
- STATUS_CODE_MAP = {...}
- CATEGORY_CD_LIST = [...]

허용
- 코드 테이블 조회용 SQL 상수
- Repository/DAO 계층을 통한 DB 조회
- 실행 시점 로드 후 컨텍스트 객체에 보관

8.2 이유

코드 테이블은 운영 DB의 기준 데이터이므로
애플리케이션 코드에 고정하면 DB와 코드 간 불일치 위험이 발생한다.

따라서 category_cd, status_cd, address_cd 등은 반드시 DB 조회 기반으로 처리한다.

8.3 권장 방식

예시 원칙
- CodeTableRepository에서 category_cd 목록 조회
- 필요한 코드값 existence check 수행
- load 직전 FK/참조값 검증 수행
- 결과는 실행 컨텍스트 범위 내에서만 재사용

9. 로깅 정책
==================================================

9.1 로깅 도구

로깅은 logger 모듈을 사용한다.

원칙
- logging.getLogger(__name__) 기반 사용
- 별도의 logger wrapper 함수는 만들지 않는다
- 각 모듈에서 직접 logger를 선언해 사용한다

예시 원칙
- 모듈 상단에서 logger = logging.getLogger(__name__)
- info: 배치 시작/종료, 건수, stage 전환
- warning: 재시도 가능 실패, 데이터 이상 징후
- error/exception: 실제 실패와 stack trace

9.2 로그와 실패 레코드의 구분

주의
- logger는 실행 로그이다.
- fail ledger/jsonl/csv는 운영 데이터이다.

즉, 아래 둘은 분리한다.
1) logger 출력
2) 실패 상태 파일 및 실패 레코드 저장

10. 글로벌 변수 금지 원칙
==================================================

10.1 금지 대상

- 실행 중 공유 상태를 담는 module-level mutable 변수
- category 목록 캐시 전역 변수
- DB 세션 전역 singleton 남용
- runtime counter 전역 변수

10.2 허용 범위

다음은 허용 가능하다.

- 불변 SQL 문자열 상수
- Enum 성격의 reason_code 문자열 상수
- 환경설정 로드용 설정 객체
- 의존성 주입으로 전달되는 config/session/repository 객체

10.3 이유

AWS Lambda 및 재실행 환경에서는
전역 상태가 예상치 못한 재사용 문제를 유발할 수 있다.
또한 상태별 독립 실행 구조와 충돌한다.

11. 모듈화 원칙
==================================================

11.1 핵심 원칙

최대한 모듈화하되, 책임이 겹치지 않게 분리한다.

반드시 분리할 책임
- 핸들러
- stage orchestration
- collectors
- parsers
- validators
- loaders
- repositories
- path builders
- models
- query constants

11.2 권장 원칙

- 함수는 한 단계의 책임만 가진다.
- 파일 저장 경로 생성과 실제 저장은 분리 가능하다.
- DB 조회와 비즈니스 판정은 분리한다.
- fail action 판정과 logger 출력은 분리한다.

12. 데코레이터 사용 원칙
==================================================

12.1 기본 원칙

데코레이터는 금지 대상은 아니지만,
사용 시 반드시 "왜 데코레이터가 필요한지"를 코드와 문서에 명확히 남겨야 한다.

12.2 허용 예

- 실행 시간 측정

1. 폐기와 삭제의 구분

본 명세서에서 폐기는 운영상 재시도 및 재처리 대상에서 제외하는 상태를 의미한다.
폐기는 물리적 삭제와 동일하지 않으며, 원본 및 실패 기록의 실제 삭제 여부는 별도 보관 기간 정책에 따른다.
폐기된 데이터는 재시도 및 재처리 대상에서 제외되며, 후속 수집 대상 선정에서도 제외될 수 있다.

2. 같은 날 재시도 금지 원칙

같은 날 재시도는 허용하지 않는다.
당일 실패 건은 다음날 이월 처리하며, 전일 전체 수집 실패 등 대규모 장애가 발생한 경우 다음 배치에서 증량 수집하거나 운영자가 알람을 기반으로 수동 실행한다.
단, 인프라 장애 등 시스템 전체 실패가 발생한 경우 해당 배치는 무효로 간주하고 재실행할 수 있다.

3. 일일 성공 기준 확정

category_cd별 일일 목표 건수는 최종 DB 적재 성공 store 100건으로 정의한다.
raw 수집 성공, parsing 성공, validation 통과 건수는 중간 지표로만 사용하며, 일일 목표 달성 여부의 기준은 load 단계에서의 store 적재 성공 건수로 판단한다.

4. 중복 판정 키 우선순위

동일 store 판정은 아래 우선순위에 따라 수행한다.

1) canonical_url
2) normalized_name + normalized_address
3) source_platform + source_internal_id

상위 우선순위 키를 사용할 수 없는 경우에만 하위 우선순위 키를 fallback으로 사용한다.
복수 키가 동시에 존재할 경우 상위 우선순위 키를 기준으로 판정하며, 하위 키는 보조 판정으로만 사용한다.

5. source platform internal id 정의

source platform internal id는 개별 크롤링 대상 플랫폼이 내부적으로 부여한 식별자를 의미한다.
이는 동일 플랫폼 내에서 동일 가게를 판별하기 위한 보조 키이며, 반드시 source_platform과 함께 묶어서 해석해야 한다.
canonical_url 및 normalized_name + normalized_address를 사용할 수 없는 경우에 한해 fallback dedup key로 사용한다.

6. idempotency 원칙

본 시스템은 AWS 재실행 환경을 고려하여 idempotent 하게 동작해야 한다.
동일 batch_id의 중복 실행, 동일 store의 중복 적재, 동일 fail 이벤트의 중복 기록이 발생하지 않도록 해야 한다.
store의 중복 판정은 canonical_url, normalized_name, normalized_address를 기준으로 하며, DB 적재 시 unique key 또는 upsert 정책을 적용하여 동일 store의 중복 insert를 방지한다.

7. Load 단계 트랜잭션 경계

Load 단계에서는 store를 핵심 엔티티로 간주하고, menu 및 review는 종속 엔티티로 분리한다.
store 적재 실패는 해당 store 전체 실패로 본다.
store 적재 성공 후 menu 또는 review 일부 실패가 발생한 경우, store는 성공으로 유지하고 실패한 종속 엔티티만 별도 fail ledger에 기록하여 재처리 대상으로 관리한다.
store 적재 성공 후 실패한 menu 및 review 데이터는 다음 실행 시 재처리 대상으로 포함될 수 있다.

8. 코드 테이블 조회 및 실행 범위 캐시

코드 테이블 값은 상수화하지 않고 DB에서 직접 조회한다.
다만 동일 실행 내 반복 조회를 줄이기 위해 핸들러 실행 범위의 메모리 캐시는 허용한다.
이 캐시는 실행 컨텍스트 내부 객체에만 보관하며, 실행 종료와 함께 폐기한다.
global 상태로 유지되는 코드값 캐시는 허용하지 않는다.

9. 파일 포맷 및 저장 기준

Raw 산출물은 원본 증거 보존을 위해 html, json, text 기반으로 저장하며 필요 시 압축을 허용한다.
Candidate, Normalized, Fail Ledger는 중첩 구조와 부분 재처리를 고려하여 JSONL을 기본 포맷으로 사용한다.
JSONL은 한 줄 단위로 독립 처리 가능하도록 설계하여 부분 재처리를 용이하게 한다.
운영 지표 파일은 일별 및 category_cd별 집계 중심의 경량 포맷으로 저장한다.

10. 보안 및 민감정보 처리 원칙

DB 접속정보, API 키, 인증 헤더, 쿠키 등 민감정보는 코드에 하드코딩하지 않고 별도 비밀 저장소를 통해 주입한다.
logger 출력 및 fail 기록에는 민감정보를 직접 남기지 않으며, 필요한 경우 마스킹 처리한다.
raw 및 fail 저장소는 최소 권한 접근 원칙과 보관 기간 정책을 적용한다.

11. 모니터링 알람 조건

모니터링 알람은 배치 기준으로 판단한다.
당일 batch의 fail ledger 누적 건수가 100건 이상인 경우 Slack warning 알람을 발송한다.
당일 batch의 load_success_rate가 80% 미만인 경우 Slack critical 알람을 발송한다.
알람 메시지에는 batch_id, target_date, category_cd, fail_count, load_success_rate, 주요 reason_code 집계를 포함한다.
critical 알람 발생 시 운영자는 즉시 상태를 확인하고 필요 시 수동 실행 또는 장애 대응을 수행한다.

12. 전일 실패분 이월 처리 원칙

전일 수집 실패 또는 대규모 장애로 인해 목표 건수를 채우지 못한 경우, 부족분은 다음날 배치로 이월한다.
이월 복구 방식은 다음날 증량 수집 또는 운영자 수동 실행으로 처리하며, 같은 날 즉시 재시도는 허용하지 않는다.
